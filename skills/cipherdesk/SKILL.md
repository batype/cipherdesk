# CipherDesk

Use the shared local API / CLI, never reimplement crypto in generated scripts. Read [references/api.md](references/api.md) for the requested algorithm's fields, byte formats and interoperability constraints.

## Run locally

Require Node 22.14+. Prefer an existing installed `cipherdesk` CLI, an installed `@batype/cipherdesk` ESM module, or the source checkout (`npm ci`, then `node bin/cipherdesk.mjs`). If installing, use the official npm registry or the user's chosen source; verify availability rather than assuming an unreleased version exists.

CLI reads one JSON request from stdin / `--in request.json` and emits JSON to stdout / `--out result.json`. Put keys, passwords and PEMs in protected local files or pass them through stdin using a programmatic process input; do not interpolate secrets in command arguments, heredocs, logs, URLs or a public issue. Use synthetic inputs for demonstrations. Do not ask the user to paste a real private key into chat when a local file can be used.

Example nonsensitive request: `{"tool":"hash","algorithm":"SHA-256","input":"abc"}`.

Check the process exit status and parse its result. Default output creation is protected against accidental overwrites; do not add `--force` unless the user's intent includes replacing that output. Use local file permissions appropriate for secrets. Display the result the user requested while avoiding unnecessary echo of private material.

## Choose and interpret correctly

- Distinguish encoding, one-way hashes, MACs, encryption and signatures. MD5/SHA/SM3 cannot be decrypted. Base64 is not secret protection.
- Use AES-GCM by default for new encryption, with fresh IV generated by the implementation. Preserve the returned envelope and the separate key/password. Do not reuse an IV from an old result for a new encryption.
- To decrypt third-party ciphertext, establish the exact mode, key bytes/encoding, IV, padding and GCM Tag / AAD convention. Request missing parameters rather than guessing. Raw GCM expects the 16-byte Tag at the end. CTR uses a 64-bit counter section.
- RSA accepts SPKI public PEM and unencrypted PKCS#8 private PEM, SHA-256 OAEP/PSS/PKCS#1 signatures. Do not silently convert or discard passphrase protection. RSA-OAEP 2048 is limited to190 plaintext bytes; use AES for larger content.
- CBC/CTR/SM4 have no authentication. Successful decoding or padding checks do not prove authenticity. ECB is compatibility only.
- JWT decoding is unverified. For verification explicitly select HS256/RS256 and inspect `details.verified`; do not treat a valid signature or exp/nbf display as complete issuer/audience/business validation.
- For password-based AES/PBKDF2 preserve salt, bit length and iterations. Defaults use600000 iterations; low values are for testing/compatibility, not a new storage recommendation.

## Verify the actual task

For new encryption, test decryption with the same key and compare bytes to the original; save keys separately from ciphertext. For a verification task report `details.verified`, including false, without converting failure into success. For conversions check the requested byte format and meaningful roundtrip. CipherDesk does not upload or persist input; the surrounding caller remains responsible for local files, clipboard and any transmission.

Limits: generally1MiB decoded input,3MiB text field, JWT64KiB. Unsupported: hash cracking, JWE, encrypted private PEM, PKCS#1 PEM, certificates, SM2, DES/3DES/RC4. State a precise unsupported requirement instead of pretending it ran.
